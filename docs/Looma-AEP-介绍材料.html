Agent-Embedded Programming · 内部培训

让 Agent
住进程序里

过去我们把 Agent 当作一个「你说什么它就做什么」的黑盒； 现在换一种思路 —— 把 Agent 当成程序里一个会思考的函数： 调用它，程序暂停；它想完、做完，程序从原地继续跑。 这就是 Agent-Embedded Programming（AEP，智能体嵌入式编程）， 而 Looma 是它的 Python 实现框架。

🧩 程序拥有 流程与验收 🤖 Agent 拥有 推理与取证据 💾 运行时拥有 暂停与恢复
Section 01

一个新范式：Agent-Embedded Programming

先用一分钟看清：过去两种用 Agent 的方式，各自卡在哪里。

📘 方式一：写一份「说明书」

这就是传统的 Skill：一段提示词、一份 SOP、一些工具使用建议，交给 Agent 去读。

✅ 即插即用，丢进会话就能读　❌ 只是一份说明，没有可执行的流程

🤖 方式二：让 Agent 自己跑

这就是传统的 Agent：给它目标，它自己规划、调工具、循环，直到自认为做完。

✅ 聪明、开放，能自主探索　❌ 智能层要自己搭，重复开发

🧩 方式三：把 Agent 嵌进程序（AEP）

流程、循环、验收条件写在 Python 里；需要判断的地方，才把控制权交给 Agent。

✅ 即插即用　✅ 能搭流程　✅ 复用宿主能力，不重复开发

🎯 AEP 的好处：三件事同时拿到

① 即插即用

沿用 Skill 的形态：一份流程就是一个普通 Python 文件，放进已经在跑的 Agent 会话里就能用 —— 不用新平台、不用新账号，也不改动宿主。

② 能搭 workflow

流程、循环、分支、重试上限都是普通 Python。可以把多次 Agent 判断串成一条 可重复执行的流水线，写在代码里、看得见、改得动。

③ 不重复开发，还简化开发

智能、工具、联网、子任务全部继承正在跑的宿主 Agent —— 不必再接一套模型接口和工具层。 更进一步：过去要在程序里手工拆成很多步、自己写编排的复杂流程，现在常常只要把一个目标交出去， 规划、调工具、必要时并行子任务都由宿主自己的强大能力完成。

一句话记住这个范式

程序负责「怎么走、什么时候算做完」，Agent 负责「怎么想、怎么找证据」，运行时负责「暂停了还能接着走」。

它的野心不是再造一个 Agent，而是改写 Agent 的使用方式：从「把任务交给一个黑盒」变成 「把智能当作普通函数来调用」—— 而调用可以跨越进程退出、Agent 执行、状态落盘、进程重启，最后依然回到原来那一行代码。

🧭
层级关系（培训中常用的说法）

AEP 是一种编程范式；Executable Skill（可执行 Skill） 是这种范式下 Skill 的新形态 —— 它不再只是说明书，而是能真正跑起来、能暂停恢复的程序； 而 Looma 是 AEP 的一个 Python 实现框架（本手册的主角）。

Section 02

三种方式的正面对比

为什么说 AEP 不是「又一个 Agent 框架」？按它的三个好处逐条对照：即插即用、能搭 workflow、不重复开发。

对比维度 传统 Skill 传统 Agent AEP（Agent-Embedded Programming）
形态是什么 一份给 Agent 看的说明书：提示词 / SOP / 工具建议 一个自主循环的智能体：目标 → 规划 → 执行 → 再规划 一个普通 Python 文件里的流程，与 for / if 平级
怎么用起来 丢进会话就能读 —— 即插即用，但只能「读」 要自己搭：模型接口、工具层、编排框架、跑起来的壳 即插即用：丢进已经在跑的 Agent 会话就能跑，不改宿主
流程谁说了算 Agent 自己，说明书只是参考 Agent 自己，人只能事后看日志 你的代码：循环、分支、重试上限都写死
能不能搭 workflow 不能，只有文字说明，没有流程 能，但走哪几步由 Agent 临场决定，不由你写死 能：多步、循环、分支、失败分支都是普通 Python，看得见、改得动
智能与工具从哪来 宿主 Agent 提供，自己不带 自己搭一套：模型接口 + 工具层 + 并发调度 直接继承正在跑的宿主 Agent：工具、联网、子任务都白得，不重复开发；很多多步编排收敛成一个「目标」交出去即可
谁在干活 全靠 Agent，程序里没有它 全靠 Agent，程序插不上手 程序出流程与验收，Agent 出判断与证据
适合什么任务 知识传递、一次性咨询 开放的探索型任务 要把多步智能判断串成一条可重复执行的工程流水线
结论：AEP = Skill 的即插即用 ＋ 可编程的 workflow ＋ 直接继承宿主 Agent 的能力。
一份流程就是一个普通 Python 文件，放进已有的 Agent 会话就能跑；流程、循环、重试上限由代码写死， 判断、找证据、调工具交给宿主 Agent —— 既不用重复搭一套智能层，也不会失去可控与可复现。 而且很多过去要自己编排的多步工作，现在交一个目标给宿主 Agent 就能完成，开发量直接变小。
Section 03

要实现这个范式，必须解决两个核心问题

把 Agent 嵌进程序，说到底就是两条方向的交接：程序怎么把活交出去，Agent 怎么把结果送回来。这两问答清楚了，范式才立得住。

核心问题一

程序的结果，怎么交给宿主 Agent？

程序跑到需要判断的那一步，得把目标、业务输入、结果应该写到哪、要满足什么结构，完整地交出去，Agent 才接得住 —— 而此刻程序随时可能退出，这些东西不能只留在内存里。

➜
需要的能力

把「交办单」结构化，并落到磁盘

交接的那一刻，把任务说明、业务输入、结果文件的位置与结构一并写下；谁来完成、隔多久完成，都不影响它接得住。

核心问题二

宿主 Agent 的结果，怎么回到程序里？

Agent 写完结果后，程序要能回到当初停下的那一行、拿到结构化的业务结果，还要能确认这就是它等的那一次交接 —— 不能接错人，也不能让它顺手带回一条你没预期要执行的命令。

➜
需要的能力

结构化结果 + 可核对的回执

结果按约定结构校验通过才使用；回来时同一条命令重跑，凭磁盘记录回到原位置，并核对「下一步要执行的命令」与当初登记的一致。

🔗
承上启下

看似只是「一去一回」，难在它要跨越进程退出、Agent 执行、时间间隔、甚至机器重启，还不能丢掉可复现性 —— 这两件事单靠业务代码补不齐，需要一个运行时兜底。下面登场的 Looma，就是干这件事的。

Section 04

Looma：AEP 的实现框架

一句话定位：Looma 是 Agent-Embedded Programming 的一个 Python 实现框架，它把上面两个核心问题的答案，收敛成三个 API。

三个 API，就是全部

没有第四个概念。学会这三行，你就学会了 Looma 的编程模型。

@workflow入口

声明「这是一个可以暂停、可以恢复的流程」。

@workflow
def main(data):
    ...
只加在最外层函数上
step(函数, 参数…)护栏

标记「这一步做过一次就会留下痕迹，只能真正执行一次」。

rows = step(read_market_data, symbol)
result = step(run_tests, repo)
说人话：写文件、写数据库、下单、发请求、跑测试或命令、调付费接口
agent(任务=…)智能边界

把需要判断的事交给宿主 Agent，程序在此暂停，它做完后从这行继续。

decision = agent(
    task="判断是否达标；未达标给出下一轮参数。",
    input={"metrics": metrics},
    output_schema=Decision,
)
它不会去调模型接口、也不会另起一个 Agent

一段完整的样子

optimize.py 
from dataclasses import dataclass
from looma import workflow, step, agent

@dataclass
class Decision:
    done: bool
    next_config: dict

@workflow
def optimize(config):
    for iteration in range(10):                     # 流程：普通 for
        metrics = step(run_experiment, config)      # 副作用：交给 step

        decision = agent(                           # 判断：交给 Agent
            task="分析结果；达标则 done=true，否则给出下一轮参数。",
            input={"iteration": iteration, "metrics": metrics, "config": config},
            output_schema=Decision,
        )

        if decision.done:                           # 验收：普通 if
            return metrics

        config = decision.next_config

它明确「不做」什么

这条边界非常关键，也是 Looma 与常见 Agent 框架最大的不同：

  • 不启动新的 Agent，不调用模型接口；
  • 不管理 API Key、会话、上下文与工具权限 —— 那些都属于宿主；
  • 不负责并发与子任务调度 —— 宿主自己有就用自己的；
  • 它只做一件事：把「暂停、保存、重放、恢复」做扎实。
💡
换个说法

Looma 不是第二个 Agent，而是程序与宿主 Agent 之间的交接与续跑层。

🧠
最容易误解的一点

decision = agent(...) 看起来像调用一个 API，实际上它的语义是：程序在这里停下、退出进程，把任务交给身边的 Agent，等它完成后再重新执行同一条命令回到这一行。

Section 05

Looma 的技术原理

程序决定流程，宿主完成判断；Looma 管理两份交接协议，以及暂停、校验与重放。

重点看这里：Agent 做完之后，脚本怎样接着执行？

恢复不是唤醒旧进程，也不是跳到某一行，而是宿主执行原命令启动新 Python 进程，Looma 重放历史事件后，让原来的 agent() 返回结果，程序再从下一行继续。

Section 05 · Product & GEPA

产品能力总览：AEP 为核心，GEPA 风格优化为可选扩展

Looma 在既有的可恢复 AEP Runtime 之上，加入了反思式候选优化所需的协议、状态、验收与 Pareto 能力；优化循环仍由应用用普通 Python 明确编排。

先看边界：评估器、样本和业务指标由应用提供；当前宿主 Agent 根据评估证据提出候选改动；Looma 负责交接、持久化、预算/约束检查和候选管理。它不会自行调用模型，也不是开箱即用的全自动搜索器。

Looma 的产品功能图

从 Python 编程接口、连续性 Runtime 和宿主交接，到诊断、Skill 与可选优化能力。

GEPA 风格闭环中，谁负责什么？

  1. 应用 / Python：定义 candidate（如 prompt、Skill 指令或 policy），实现 evaluator 和评分维度；用 step() 保存评估，避免 replay 重复执行。
  2. 宿主 Agent：读取 parent 的 scores，以及可选 trajectory、objective scores 和 ASI，提出结构化 CandidateProposal。
  3. Looma：把反思作为 agent() 交接；程序再评估 proposal，并用确定性验收门检查修改范围、硬约束、预算与分数。
  4. Pareto frontier：保留非支配或跨样本互补候选，按稳定规则选择下一轮 parent；达到轮数、预算、阈值或 patience 后停止。

与“自动搜索器”的区别

搜索循环的控制权、评价函数和业务成功标准仍在 Python Workflow。Looma 提供 GEPA 风格的反思输入/候选协议、状态与 Pareto/验收工具；宿主 Agent 负责语义改进，但 Looma 不会自行启动 Agent、批量探索模型候选或替应用决定指标。这样可以把搜索预算、回归门槛和最终接纳条件显式留在业务代码中。

一次优化迭代如何运行

循环不是隐藏在 Runtime 里的黑盒：每轮评估、反思、再评估和接纳都能在 Workflow 中检查和调整。

上手：跑起来

原理讲完了，动手只需要三步。

① 安装

terminal 
pip install https://github.com/datanger/Looma/releases/download/v0.1.4/looma_runtime-0.1.4-py3-none-any.whl

# 或源码方式
git clone https://github.com/datanger/Looma.git
cd Looma && pip install -e .

要求 Python 3.10+，无需任何 API Key。

② 写流程

在已经运行的 Agent 会话里，按第 04 节的写法写一个 @workflow 函数。

三条口诀：流程用 Python、副作用包 step()、判断交给 agent()。写完直接运行，不需要注册任何服务、也不需要配置模型。

③ 运行与继续

terminal 
python optimize.py    # 第一次：跑到需要判断处停下等待
python optimize.py    # 继续：同一条命令，自动从原位置往下走

不需要写续跑脚本，也不需要记住任何编号。

✅
核心体验

整个使用体验就是：写下流程 → 反复执行同一条命令。中间需要什么判断，程序自己会停下来找 Agent。

Section 07

循环、重试与失败分支

这三件最常见的事，都只是普通 Python —— 运行时里没有隐藏的「自动重试黑盒」。

自愈循环：测试 → 分析 → 修复

repair.py 
@workflow
def repair(repo):
    # 重试上限写死在代码里：就是一个普通 for
    for attempt in range(5):
        tests = step(run_tests, repo)

        review = agent(
            task="判断测试是否已经通过；未通过则给出修复方案。",
            input={"attempt": attempt, "tests": tests},
            output_schema=dict,
        )

        if review["done"]:
            return tests

        step(apply_fix, repo, review["fix"])

每一轮都是一次独立记录；恢复后会自动回到正确的那一轮。

失败也是普通分支

🚨
铁律

外部数据拿不到时，可以请 Agent 去找，但不允许为了流程能继续而编造、估算、插值事实。证据不足就明确输出「证据不足」或直接失败。

验收判定：别只听 Agent 说「我完成了」

Agent 提供的是语义判断；而「到底算不算完成」应当尽量由代码来判定 —— 文件有没有产出、引用的来源是不是真的读过、数值有没有落在合理区间、结构是否符合约定。这些能写成代码的，就不要交给 Agent 自述。

Section 08

状态、目录与调试

所有进度都落在磁盘上，而且写入是原子完成的 —— 中途断电也不会留下半截记录。

📁 工作目录长什么样

.looma/
├── invocations/               # 哪条命令 ↔ 哪次进度
└── runs/
    └── <本次运行编号>/
        ├── state.json         # 流程状态
        └── events/
            ├── 0000-step-result.json    # 步骤结果
            ├── 0001-script2agent.json   # 任务说明
            └── 0001-agent-result.json   # Agent 的结果

跑完或失败的记录会释放「当前进度」指针，但历史记录都留着可查。

🧰 常用命令

terminal 
looma status              # 看本地有哪些运行记录
looma inspect             # 看最近一次运行的详细过程
looma inspect <编号>      # 看指定那一次
looma skill-path          # 查看随包提供的可执行 Skill
looma reset --yes         # 清空本地状态（开发期常用）
looma handoff --request … --response …
    # 校验 Agent 交回的「下一步命令」，一致才继续
🔀
同一条命令要跑多份互不干扰的流程

LOOMA_RUN_KEY=任务A python main.py —— 不同标识得到各自独立的进度记录（这是实例隔离，不是并发执行）。

🧯
如果提示「历史对不上」

说明当前代码路径与记录下来的过程不一致（比如中途改了流程顺序、或者某次恢复走了不同分支）。运行时会直接报错而不会猜着往下走 —— 开发期最快的办法是 looma reset --yes 清掉状态重跑。

这个流程实际怎么跑：一次完整运行走一遍

上面那张图讲「哪些该由代码做」，这里讲一次运行是怎么在程序与宿主之间来回的。以 --name 宇树科技 --symbol 688836 这一次为例，每一步都标清谁在做；两条红线是两次进程边界。

① 用户
在宿主 Agent 的会话里说一句：「把这条命令跑起来」，附上标的与参数。这是整条链路的起点。
▼
② 宿主 Agent
真的去执行：python examples/stock_analysis_agent/workflow.py --name 宇树科技 --symbol 688836。所有「执行」都是它做的 —— 程序不会自己跑起来，恢复执行也一样。
▼
③ 你的程序
解析标的 → 先用确定性方式取真实行情（step() 登记：这一刻的行情只取一次、结果落盘）→ 计算市场特征。
▼
④ 你的程序
取不到 → 走到需要判断的地方（agent()）：把补什么数据、结果写到哪个文件、要满足什么结构连同当前进度写成 script2agent 落到磁盘，然后结束进程。
进程边界 · 程序真的退出了，而不是挂起等待
⑤ 宿主 Agent
读 script2agent，用自己的联网能力找到带来源的真实行情（禁止编造、估算价格），必要时自行并发子任务。
▼
⑥ 宿主 Agent
把业务结果按约定结构写进结果文件 —— 这个路径就写在它刚才读到的那张单子里。
▼
⑦ 校验
由宿主 Agent 执行校验（looma handoff），两道核对缺一不可：结果文件的结构是否符合约定？下一步要执行的命令是否与当初登记的那条完全一致？
任何一道不过，就在这里停住，不允许继续执行。
▼
⑧ 宿主 Agent
把 agent2script 保存为 JSON，并执行 looma handoff --request … --response …。Looma 先校验结果文件结构与恢复命令；两项都通过后，handoff 才执行 script + args 指向的原始命令，启动新的 Python 进程。
进程边界 · 同一条命令被重新执行
⑨ 你的程序
新进程从入口重跑：已取过的行情、已算过的特征、已问过 Agent 的地方，全部直接读回历史 step() / agent() 事件（不重复执行 —— 不重复取数、不重复花钱），直到原 agent() 读取宿主写下的结果并返回，程序再从下一行继续。
▼
⑩ 你的程序
继续往下跑：交给 Agent 检索近期新闻 → 证据完整性检查（由代码判定）→ 不够就定向补研（可循环，轮次上限写死在代码里）→ 多角度分析 → 分析校验 → 渲染报告，最后输出「完成」或「证据不足」。
🔑
抓住两个关键

1）每一步的执行者都是宿主 Agent：跑程序是它跑的、联网找数是它找的、写结果是它写的、校验与恢复执行也是它做的。程序只负责说清「到哪一步该停、要写什么、该校验什么」。
2）第 ④~⑨ 步这一圈会在每个 agent() 处重来一次；「停」不是挂起，是进程真的退出；「继续」不是恢复内存，而是同一条命令重新执行 + 把已完成的步骤重放一遍 —— 靠的是磁盘上的记录，不是残留的内存。

Section 10

避坑清单

按这两栏对一遍，基本不会跑偏。

✅ 应该这样做

  • 流程、循环、重试上限都用普通 Python 写。
  • 有副作用的操作一律包进 step()。
  • 跨边界的数据保持可序列化（普通字典 / 数据类）。
  • 给 Agent 的结果声明结构，让它必须按格式回。
  • 继续时重跑原来那条命令。
  • 能写成代码的验收条件，就不要交给 Agent 自述。
  • 外部事实保留来源，证据不足就如实说不足。

🚫 千万不要这样做

  • 在流程里再写一套模型接口配置。
  • 从流程里去调用别的 Agent 命令行或 SDK。
  • 把 Looma 当成第二个 Agent 来用。
  • 为每次交给 Agent 的任务都造一个续跑脚本。
  • 把业务结果塞进返回给程序的命令里。
  • 结果还没写回来就执行下一步。
  • 为了让格式校验通过而编造业务事实。
一句话速查要点
范式AEP：程序管流程与验收，Agent 管判断与证据，运行时管暂停与恢复
三个 API@workflow 入口 · step() 只执行一次 · agent() 暂停等判断
三条通道任务说明交出去 · 结果文件收回来 · 恢复回执要对得上
三个关口进去校验输入、回来校验结果、继续前校验命令一致
恢复方式重跑原来那条命令，历史直接重放，不重复副作用
运行环境纯 Python 包，Python 3.10+，不需要任何 API Key
边界不调模型、不启动 Agent、不管并发；并发与子任务属于宿主
